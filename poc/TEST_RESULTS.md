## 4. Property-based stress test (`tests/test_property_abstain_or_correct.py`, `runtime/pbt_stats_*.json`)
**Property:** the output is REJECT, or ACCEPT with critical fields exactly equal to ground truth. Documents with a defect must be REJECTED.

Each case combines a random report, 0–3 valid variations, optionally 1 defect, and 0–2 new fuzz operations: a free-text comment line in the table, a blank line, a changed result digit, and random character damage on static lines. This test was written **after** the freeze and the first held-out run.

| Run | Cases | Silent errors | Unsafe accepts (data correct?) | Correct accept | Correct reject | Rejected valid |
|---|---:|---:|---|---:|---:|---:|
| **v1 (frozen system)** | 3,000 | **2** | 2 (both data-correct) | 1,614 | 728 | 654 |
| v2 default seed | 3,000 | 0 | 3 (all data-correct) | 1,628 | 756 | 613 |
| v2 seed 424242 | 5,000 | 0 | 4 (all data-correct) | 2,675 | 1,356 | 965 |
| v2 seed 777 | 5,000 | 0 | 0 | 2,626 | 1,374 | 1,000 |

**The v1 silent errors were real.** Character damage on page 1's column header ("UNIT" → "UNQT") stopped the table-start pattern matching there. The table then began at page 2's repeated header, page-1 rows were **silently dropped**, and the document was accepted with fewer results.
- The coverage check only covered start…end.
- **v2 fix:** reject if any result-like row appears outside the parsed table (`interpreter.py`, `rows_outside_table`).
- The fix is generic (it doesn't mention layouts). Held-out outcomes are unchanged.

**The remaining unsafe accepts:** all are layout A with `header_changed` and `page_break`. My generator prints the *new* header on page 1 but the *old* lab name on page 2, so the old anchor still matches. In every case the extracted data was fully correct. The underlying weakness is that anchors may match anywhere in the document, not at a fixed position. The test still **fails** on these, deliberately.

**The "rejected valid" column is not a refusal metric:**
- Comment lines are always rejected by design (unexpected table content).
- A changed digit can create a genuinely implausible value while the test still expects ACCEPT.

### Real OS spooler: macOS CUPS → `socket://127.0.0.1:9100` (temporary queue, removed afterwards)
- macOS refused a "raw" model ("Raw queues are no longer supported on macOS"). The queue was created without a printer driver and jobs were sent with `lp -o raw`.
- **C1:** plain-text layout A, ESC/P layout B and multi-line layout C were delivered. **SHA-256 matched at source file, capture and printer for all 3.** All 3 were ACCEPTED (lab-a, lab-b, lab-c) and FHIR was written.
- **C2, listener offline:** CUPS showed "The printer is not responding", kept the job and retried. The job was **delivered once**, about 24 s after the listener restarted.
- Clean up verified: `lpstat -p` shows no destinations.

## 7. Direct-LLM baseline (`runtime/baseline_summary.json`, `runtime/baseline_rows.jsonl`)
**Setup:**
- 128 held-out docs: 5 clean + 1 of each perturbation per layout.
- Same model (sonnet) and the same dictionary and field definitions.
- The prompt allows and encourages refusal.

**Not scored (8):**
- 6 truncated docs were **blocked by the pre-send guard**, because truncation removed the synthetic marker. The guard worked as intended.
- 2 outputs were unparseable.

| | Direct LLM | Spoolgeist (the same 120 docs) |
|---|---|---|
| Valid docs accepted correctly | 29/58 | 54/58 |
| **Wrong values on accepted valid docs** | **0** | **0** |
| Invalid docs accepted | 6/62. **All 6 had correct data**: `header_changed` ×3 and `layout_drift` ×2 are invalid only for a *template*; the `unknown_test` ×1 typo label was mapped to the right test | 0/62 |
| Refusals of valid docs | 29/58. Mostly **physiological inconsistency in my synthetic CBCs** (MCV/MCH/MCHC don't match Hb/Hct/RBC; NEUT% + LYMPH% > 100; direct bilirubin > total), plus ambiguous MM/DD dates and sex vs reference-range mismatches | 4/58 (long names) |
| Cost / latency per document | ≈ US$0.025, median 7.5 s, cloud call with document content | US$0, 0.3 ms, local, no AI |
| LLM output + our validators | identical outcome counts (validators added nothing here) | — |

**Interpretation (important):** in this benchmark the direct LLM did **not** produce confident wrong values. The planned demo claim, "direct LLM extraction silently gets it wrong", is **not supported** by our data. What is supported:
- **Reproducibility:** the same input gives the same output, with a pinned rule hash.
- **Cost and latency:** about 25,000× faster and with no per-document cost.
- **Privacy:** no AI at runtime.
- **A provable fail-closed property under test.**

The LLM also showed an advantage: clinical cross-checks that our validators lack.
